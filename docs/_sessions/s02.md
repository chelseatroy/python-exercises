2. **Select** a test framework. You can use unittest or [pytest](https://docs.pytest.org/en/stable/getting-started.html), student’s choice. The tests I am providing you with will run in both (they’re unittest tests, and pytest runs unittest tests without changes).

3. Copy both of these files, [table.py](../../downloads/table.py){:download=""} and [test\_table.py](../../downloads/test_table.py){:download=""}, into your homework-2 directory. It’s an implementation file and a test file. 

   Take a second to look around. What’s in these files? What does the class in the implementation file do? *At a minimum,* you should find the unit tests extremely helpful for explaining what the implementation class does.

4. Run the tests. Notice that all the tests pass except for *one*. What is that test checking for? Why is it failing? Your first task is to get this test passing by making changes to the implementation. 

   Technically, you only have to change *two lines* to get this test passing, and you don’t have to add or remove any lines (though there is one line you *can* remove once you’ve made the changes).

5. Now your failing test passes, but the *deletion* tests fail. Why? Decide how to fix deletion so that now *all* of the tests are passing. You should not need to make changes to *the tests themselves* at all up to this point in the homework. 

6. Okay, **this is the first time you will change the test suite.** Currently the Table supports only two states: *in* a transaction, and *out of* a transaction. Please add a test that ensures support for **nested transactions.** The implementation should support arbitrarily deep stacks of nested transactions, but it’s okay if your test just checks for three. You can add your test in the original test file or in a new test file, students’ choice (there are valid engineering arguments for either choice).

   <mark>In a nested transaction sequence, the user can nest begin-commit pairs. Committing the outermost transaction modifies the main data, like it does now. Committing an inner transaction modifies the data of the next outer transaction. Rolling back an inner transaction discards the changes, as it does now; rolling back an outer transaction discards the changes of that transaction</mark> *<mark>and any inner transactions</mark>*. 

   Any inner transaction is either committed or rolled back inside of an outer transaction; there is no committing an outer transaction before one of its inner transactions is closed. 

   

7. Change the implementation to support nested transactions.

   

8. Add tests to ensure that commit and rollback *both* work, and that adding, updating, and *deleting* columns all still work as well. You still shouldn’t need to change anything in the tests I originally gave you; you’re just *adding* tests.

   

9. Make any implementation changes you need to to ensure that your additional tests also pass. So, to summarize, now *all the tests should pass*: the ones *you* wrote and the ones I gave you.
