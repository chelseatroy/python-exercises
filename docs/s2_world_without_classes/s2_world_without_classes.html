Session 2 · State and behavior, without classes

A World Without Classes

Suppose a programming language had no classes. Just ints, strings, booleans, lists, and dictionaries. Could we still bundle what a thing is (its state) with what it can do (its behavior)? Let's build some shapes and find out.

What are classes for, anyway?

Answer in the chat first.
Keep state togetherAn order has a buyer, a seller, a price, a product, and order and ship dates. A class keeps them all in one place.
Pass it around as one thingLike keeping beads sorted in a bag per color. You carry the bag, not each bead.
Attach behavior that guards the stateIf the only way to ship an order is mark_shipped(), that method can refuse a ship date before the order date. Then you can trust the data.

Not everyone wants this. Plenty of Haskell (and some Rust) programmers will tell you state and behavior don't belong together. We'll take up that argument in a later session.

Functions are values too, so they can go in a dict. lambda makes a function without giving it a name. Put every circle function in one bag, then copy the bag into each new circle with update.

What does update give back? Guess first.
      

        
another_circle = {"radius": 7}.update(circle_behavior)
print(another_circle)   # None

        
update changes the dict in place. In-place operations in Python, like list.sort() and dict.update(), return None, not the changed object. Make the dict first, then update it.

5. Copy down, or look up?

    
Copy-down copies rectangle's entries at the moment you build the square. The other option: give the square a "super" entry that points at rectangle_behavior, and when the square doesn't have something, go look there. Same square, built both ways.


    


    

      

        Look up

square_behavior[name]

          

          
    
          
    
        
    
        
    
          
    Look up through "super"
    
          
    def look_up(behavior, name):
    while behavior is not None:
        if name in behavior:
            return behavior[name]
        behavior = behavior.get("super")
    raise KeyError(name)
    
          
    
          
      
          
      
        
      
      
      
    
      

    
      
      
      Which one does Python do?
      Answer in the chat first. Then say why.      
      
      
        
      Python looks up. A class keeps a reference to its parent, and when it doesn't have a name, Python goes and checks the parent, then the parent's parent, and so on.
      
        
      It has to, because Python lets you add things to a class after you've made it, like this: Rectangle.diagonal = lambda self: .... Every subclass sees the change right away. With copy-down, subclasses made earlier would never see it. That's exactly what happened to "diagonal" above.
      
        
      JavaScript works the same way. Its "prototype chain" is this same "super" pointer.
      
      
      
    
      

    
      
      
      So why would anyone copy down?
      Think speed, space, simplicity, capability.      
      
      
        
      
          
      Speed: copy-down winsEvery lookup searches one dict. No hopping. Each hop up the chain is another dict to search, and chains can be long.
      
          
      Space: look-up winsCopy-down stores its own copy of every inherited entry, in every subclass.
      
          
      Capability: look-up winsChange the parent, and every child sees it, even children made earlier.
      
        
      
        
      Copy-down is one of the oldest ways to build inheritance, because it's fast: everything a subclass needs sits together, ready to go. Statically typed languages like Java and C++ lean this way. Each class gets a table of its methods with the parent's entries copied in. Those languages don't let you add methods to a class after the fact, so the copy never goes stale.
      
        
      Python chose the capability and paid for it in speed. This is one reason Python has a reputation for being slow. It keeps choosing flexibility, like dynamic typing: types are checked as the program runs, not before.
      
      
      
    
      
  
      

  
  
      
    
      6. Meanwhile, in a world with classes
      
    
      Here are the same shapes as real Python classes.
      
    
      
      
      class Rectangle:
    angle_size = 90

    def __init__(self, length, width):
        self.length = length
        self.width = width

    def area(self):
        return self.length * self.width

    def perimeter(self):
        return (2 * self.length) + (2 * self.width)

class Square(Rectangle):
    def __init__(self, side_length):
        super().__init__(side_length, side_length)

    def area(self):
        return self.length ** 2

    def perimeter(self):
        return 4 * self.length
      
      
      
        
      Look underneath
      Where's the state? Where's the behavior? Where's the parent? Guess first.      
        
      
          
      >>> sq = Square(4)
>>> sq.__dict__                  # the bag of state
{'length': 4, 'width': 4}
>>> [k for k in Square.__dict__ if not k.startswith("__")]
['area', 'perimeter']          # the bag of behavior
>>> Square.__bases__             # the "super" pointer
(<class '__main__.Rectangle'>,)
>>> sq.angle_size                # not in Square, so look up
90
>>> import math
>>> Rectangle.diagonal = lambda self: math.sqrt(self.length**2 + self.width**2)
>>> sq.diagonal()                # added after sq was made, still found
5.656854249492381
>>> Rectangle.__bases__          # the chain ends at object
(<class 'object'>,)
>>> sq.area() == Square.__dict__["area"](sq)
True                         # the clunky call, done for you
      
          
      Run in CPython 3.10. Square.__dict__ also holds housekeeping entries like __init__, __module__, and __doc__. The list above leaves those out.
