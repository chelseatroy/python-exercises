The Growing List

A Python list is two things: a small header that every name points to, and a separate block of slots that the header points to. Each slot holds a pointer to an object, never the object itself. When the block runs out of slots, CPython gets a bigger block. What happens to the names when it does?

    sys.getsizeof here is 56 bytes for the header plus 8 bytes per slot, which is what a 64-bit CPython 3.8 or newer reports. It counts the slots, not the objects they point to. Addresses are made up, but they change when real ones would.

    Questions to argue about

    Why not grow by exactly one slot each time?

    Guess first. Then try "No spare room" and watch pointers copied.

    Every time the block moves, every pointer in it gets copied to the new block. If the list grew by exactly one slot per append, appending item number n would copy n − 1 pointers. Building a list of 1,000 items that way copies about 500,000 pointers.

    Growing by about one eighth plus a little (CPython's rule) means the moves get rarer as the list gets longer. The total copying stays proportional to the length of the list, so each append costs a constant amount on average. That's what "amortized O(1)" means.

    The price is space: about one slot in nine can sit empty. That's the same space-for-speed trade as caching.

    Why wait until the list is half empty to shrink?

    Look at the check on line 44 of the code your instructor links, then try "Pop below half".

    The check is allocated >= newsize && newsize >= (allocated >> 1): "there's already room, and we're still using at least half of it." When that's true, CPython only changes the length. Nothing moves.

    Imagine shrinking as soon as there was any spare room instead. A list sitting right at a boundary that alternates append, pop, append, pop would move its whole block on every single call. Waiting until it's half empty leaves a wide gap between "grow" and "shrink", so that back-and-forth costs nothing.

    Since October 2026 (gh-158592), CPython also never shrinks a block of 32 slots or fewer. Moving a small block costs more than the memory it gives back. Switch the rules to "newest" and pop again.

    The growth pattern changed. When, and why?

    Compare "CPython ≤ 3.8" with "3.9 – 3.15.0" after filling to 30.

    The code linked from class is from 2018. Its comment says the growth pattern is 0, 4, 8, 16, 25, 35, 46, 58, 72, 88. Run the experiment on a current Python and you'll get 0, 4, 8, 16, 24, 32, 40, 52, 64, 76. Somebody changed it. The commit history can tell you who, when, and why:

    git log -L:list_resize:Objects/listobject.c

    The same command, pointed at list_sort_impl, is how we'll look at sorting next.
