Session 3 · How a list works under the hood

The Growing List

A Python list is two things: a small header that every name points to, and a separate block: one unbroken run of memory, cut into 8-byte slots. Each slot holds a pointer to an object, never the object itself. When the block runs out of slots, CPython gets a bigger block and copies the pointers over. What happens to the names when it does?

      The slots in a block sit back to back, 8 bytes apart, which is how a[i] is found with one multiplication. sys.getsizeof here is 56 bytes for the header plus 8 bytes per slot, which is what a 64-bit CPython 3.8 or newer reports. It counts the slots, not the objects they point to.

      Why does almost every resize move the block? Every block on this page is 512 bytes or smaller, so it comes from CPython's own small-object allocator. That allocator hands out memory in cells whose sizes are 16 bytes apart, and realloc() can only keep a block where it is if the new size still fits its cell (and doesn't waste more than a quarter of it). A list resize usually adds at least 32 bytes, so it nearly always needs a new cell. Bigger blocks work differently: see Where Blocks Live. Addresses here are made up.

      What does >> do?

      An integer is stored as binary digits, called bits. x >> k ("shift right by k") slides all of its bits k places to the right. The k bits on the right end fall off and are thrown away, and zeros come in on the left.

      Each place in binary is worth twice the place to its right, so sliding every bit one place right halves the number, and throwing away the bit that fell off rounds down. Slide 3 places and you've halved three times: newsize >> 3 is newsize // 8. Line 122's allocated >> 1 is allocated // 2, "half of what's allocated".

      Why write newsize >> 3 instead of newsize / 8?

      1. Speed, historically. A shift is one of the cheapest things a CPU can do: one instruction that finishes in a single clock tick. Division used to take dozens of ticks. list_resize() runs every time a list needs a new block, so C programmers reached for the shift.
      2. It still saves a little. Today a compiler turns / 8 into a shift on its own, but not quite for free here. newsize has a signed type (Py_ssize_t), and C's / must round negative numbers toward zero, so the compiler adds a couple of instructions to handle negatives first. A list's length is never negative, and >> 3 skips that fix-up.
      3. It reads as "about an eighth". To a C programmer, newsize >> 3 says "a fraction of the size, cheaply" at a glance. The exact fraction doesn't matter. What matters is that the spare room grows in proportion to the list, which is what makes appends cost O(1) on average (see the first question below).

      Python has the same operator: try 17 >> 3, and bin(17), bin(17 >> 3). It's the same binary as Session 1.

      And the & ~(size_t)3 at the end of line 148?

      This part was added in Python 3.9. ~3 flips every bit of 3, turning …00000011 into …11111100. & keeps a bit only where both sides have a 1, so & ~3 clears the last two bits, the 1s place and the 2s place. Whatever's left is a multiple of 4: it rounds down to a multiple of 4. The source comment says it plainly: "Add padding to make the allocated size multiple of 4." That's why lists now grow 16, 24, 32 where they used to grow 16, 25, 35. The slider above shows this one too.

      Why not just "clear the last two bits"? (Why bitmasks exist)

      Flipping 3 seems like a strange way to round down. Guess why C does it this way.

      C has no operator for "clear the last two bits." Its whole toolkit for bits is six operators: & (AND), | (OR), ^ (XOR), ~ (NOT), << and >> (shifts). None of them takes a list of positions. Python's integers have the same six, and no more.

      So instead you build a bitmask: a number whose bits mark the positions you care about. Then one operator applies it to every position at once:

      x        =    0001 1001   25

~3       =    1111 1100        the mask: 0 means "clear this bit"
x & ~3   =    0001 1000   24   clear the last two bits

3        =    0000 0011        the mask: 1 means "this bit"
x | 3    =    0001 1011   27   set them
x ^ 3    =    0001 1010   26   flip them
x & 1    =    0000 0001    1   test one bit: is x odd?

      To clear bits, the mask needs 0s in those places and 1s everywhere else. For a 64-bit number, that's 62 ones and then 00: 0xFFFFFFFFFFFFFFFC. Nobody wants to type that, and it only works at one width. So C programmers write the bits they want gone, 3, and let ~ flip it into the mask. Read x & ~3 as "x, without the bits in 3." The compiler works out ~(size_t)3 once, while compiling, so the running program does a single &.

      Bitmasks are everywhere once you start looking:

      • The dict from Session 2. The Hash Ring found a bucket with hash % size. CPython actually writes hash & (size - 1). When size is a power of 2, size - 1 is all 1s (8 − 1 = 0111), so the & keeps just the remainder, with no division. Another reason dict sizes are powers of 2.
      • Flags. re.compile(pattern, re.IGNORECASE | re.MULTILINE) packs two on/off settings into one number, one bit each.
      • File permissions. chmod 755 is three groups of three bits: read, write, execute.

      Try it in Python: 25 & ~3, bin(25 | 3), 25 ^ 3. One surprise: ~3 prints -4. Python's integers are signed, and "all 1s ending in 00" is how a computer stores −4. It's the same bit pattern, so 25 & ~3 is still 24.

      Questions to argue about

      Why not grow by exactly one slot each time?

      Guess first. Then do step 6 and watch pointers copied.

      Every time the block moves, every pointer in it gets copied to the new block. If the list grew by exactly one slot per append, appending item number n would copy about n pointers. Building a list of 1,000 items that way copies about 500,000 pointers.

      Growing by about one eighth plus a little (CPython's rule) means the moves get rarer as the list gets longer. The total copying stays proportional to the length of the list, so each append costs a constant amount on average. That's what "amortized O(1)" means.

      The price is space: about one slot in nine can sit empty. That's the same space-for-speed trade as caching.

      Why wait until the list is half empty to shrink?

      Look at the check on lines 121–122 above, then do step 5.

      Start with the first two parts of the check, allocated >= newsize && newsize >= (allocated >> 1): "there's already room, and we're still using at least half of it." When that's true, CPython only changes the length. Nothing moves.

      Imagine shrinking as soon as there was any spare room instead. A list sitting right at a boundary that alternates append, pop, append, pop would move its whole block on every single call. Waiting until it's half empty leaves a wide gap between "grow" and "shrink", so that back-and-forth costs nothing.

      The last part, || allocated <= LIST_SMALL_ALLOCATED, is brand new: it arrived in October 2026 (gh-158592), so Python 3.15.0 and earlier don't have it. LIST_SMALL_ALLOCATED is 32 (line 94), so CPython now never shrinks a block of 32 slots or fewer. Moving a small block costs more than the memory it gives back. Step 5 lets you try both.
