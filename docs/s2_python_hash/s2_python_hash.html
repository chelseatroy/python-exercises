What Hash Does Python Use?

There isn't just one. hash(x) asks x's type to hash it, and each type has its own recipe. Strings get a cryptographic hash with a secret key. Integers mostly hash to themselves. Tuples mix their items' hashes together. Step through each one below, and see why strings needed the secret key in the first place.

hash() asks the key's type

Type a Python value, or pick one. hash(x) calls type(x).__hash__(x), so the type decides which recipe runs.

Strings: SipHash-1-3

CPython hashes the string's bytes with SipHash-1-3, mixed with a 128-bit secret key it picks at random every time Python starts. Four 64-bit numbers, v0 to v3, get stirred together with the bytes, 8 at a time. "1-3" means 1 round of stirring per block of 8 bytes, then 3 rounds at the end.

Change one letter

A good hash changes about half its bits when the input changes even a little. That's called the avalanche effect. It's why 'user_1' and 'user_2' don't end up in neighboring buckets.

Where it came from

  • Python 3.4 to 3.10: SipHash-2-4, adopted in PEP 456. Before that, strings used a simple multiply-and-XOR hash (FNV-style).
  • Python 3.11 and later: SipHash-1-3, with fewer rounds, which makes it faster (the discussion). Rust's standard HashMap uses SipHash-1-3 too.
  • The four starting constants are ASCII text: 0x736f6d6570736575 spells "somepseu", and together they spell "somepseudorandomlygeneratedbytes".
  • A string remembers its hash. CPython stores the hash inside the string object the first time it's computed, so using the same string as a key again costs nothing.
  • bytes uses the same function. A str is hashed as the bytes CPython stores it in: 1, 2 or 4 bytes per character, depending on its widest character.

Check your own Python: import sys; sys.hash_info.algorithm prints 'siphash13'.

Integers: the remainder mod 261 − 1

An int's hash is its remainder after dividing by P = 2**61 - 1 = 2305843009213693951, a prime. So hash(42) == 42, and every int up to about 2.3 quintillion hashes to itself. There's no secret key: the same int has the same hash in every Python process. Negative numbers keep their sign.

Why cutting into pieces works

It's the same trick as dividing by 999 in base 10. Since 1000 is 1 more than 999, 1000 leaves a remainder of 1, and so does every power of 1000. So to find 123,456 mod 999, add the 3-digit groups: 123 + 456 = 579. No long division.

In binary, 261 is 1 more than P, so the same thing works with 61-bit pieces. CPython's long_hash does it with shifts, ANDs and adds: no division at all. A prime of the form 2n − 1 is called a Mersenne prime.

Things to notice

  • hash(-1) is -2. In CPython's C code, a hash function returns -1 to mean "an error happened," so no hash is ever allowed to be -1. That's why hash(-1) == hash(-2).
  • hash(2**61 - 1) is 0, and so is the hash of every multiple of P. Keep that in mind for hash flooding, below.
  • True and False are ints (bool is a subclass of int), so hash(True) == 1.
  • On a 32-bit build, everything here uses 231 − 1 instead.

Floats: equal numbers, equal hashes

Python requires that a == b implies hash(a) == hash(b). Since 1 == 1.0, a float has to hash the same as the int it equals. So floats use the same remainder: every float is exactly some whole number m times a power of 2, m × 2**e, and its hash is that value mod P. Multiplying by a power of 2 mod P turns out to be a rotation of the bits.

That's why {1: 'one'}[1.0] finds 'one'. Why is hash(0.5) == 2**60? Because 2 × 260 = 261, which is 1 more than P. So mod P, 260 acts like ½.

The odd ones

  • hash(float('inf')) is 314159, the first digits of π. -inf gives -314159.
  • nan isn't equal to anything, not even itself. Since Python 3.10, each nan object hashes by its identity, like a plain object(). Before that, every nan hashed to 0.
  • complex combines the two parts: hash(real) + 1000003 * hash(imag), so hash(1j) == 1000003.

Tuples: mix the items' hashes

A tuple hashes each item, then folds those hashes into one 64-bit accumulator: add, rotate, multiply, once per item. The constants are big primes borrowed from xxHash, a fast non-cryptographic hash. This recipe arrived in Python 3.8.

hash( )

Why not just XOR the item hashes together?

XOR is cheap, and older recipes used ideas like it. But XOR doesn't care about order, and anything XOR'd with itself is 0:

TupleXOR of item hashesPython's hash()

Coordinates like (x, y) are common dict keys, and so are pairs with the same item twice. With XOR, every (n, n) would land in the same bucket. Rotating and multiplying after each item makes the position of an item matter.

Your own objects: the address, rotated

A class that doesn't define __eq__ or __hash__ gets the default: two objects are equal only if they're the same object. So the hash only has to match for the same object, and CPython uses its memory address, which is what id() returns. But first it rotates the address right by 4 bits.

Each click makes a new object at a new address.

Why rotate?

A dict picks a bucket from the lowest bits of the hash: hash & (size - 1). Object addresses are multiples of 16, so their lowest 4 bits are always 0000. Drop 12 objects into a 16-bucket dict, with and without the rotation:

bucket = id(o) & 15
bucket = hash(o) & 15 (rotated first)

And None?

None used to hash by its address too, so its hash changed from run to run. That made the order of a set like {None, 1, 2} change between runs. Since Python 3.12, hash(None) is always 4238894112 (0xFCA86420 in hex) (the discussion).

Strings still change between runs on purpose, so a set of strings still prints in a different order each time. Try python3 -c "print({'a', 'b', 'c'})" a few times.

Lists don't get a hash

hash([1, 2]) raises TypeError: unhashable type: 'list'. Why not just hash the items, like a tuple does? Because a list can change after it's in the dict. Suppose lists hashed like tuples:


      

    

    

      
Two rules for __hash__

      
    
        
  1. If a == b, then hash(a) == hash(b). Otherwise a dict looks in the wrong bucket for a key it already has.
    2. 
        
  2. A key's hash must never change while it's in a dict.
    3. 
      

      
Because of rule 1, if your class defines __eq__ and not __hash__, Python sets __hash__ to None, and its objects become unhashable. To get the hash back, hash the same fields __eq__ compares, by putting them in a tuple:

      
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)
    def __hash__(self):                 # without this: TypeError: unhashable type: 'Point'
        return hash((self.x, self.y))   # equal points → equal tuples → equal hashes

      
Rule 2 is your job: don't change x or y after a Point goes into a dict. @dataclass(frozen=True) writes __eq__ and __hash__ for you, and won't let the fields change.

    

  


  
  

    
Why strings need a secret key: hash flooding

    
Web frameworks put request data into dicts: form fields, query parameters, JSON object keys. If an attacker can predict your hash function, they can send thousands of keys that all have the same hash. Each new key then has to walk past every key before it, and a lookup that should be O(1) becomes O(n). Inserting n keys costs about n²/2 checks.

Try it in Python

        
Int hashes aren't secret. Every multiple of P hashes to 0, so you can flood a set yourself:

        
import time
P = 2**61 - 1
for n in (1_000, 2_000, 4_000, 8_000):
    flood = [i * P for i in range(n)]  # all hash to 0
    start = time.perf_counter()
    set(flood)
    print(n, time.perf_counter() - start)

So why aren't ints protected too? Keeping hash(n) == n makes ints fast to hash, and data from outside a program (form fields, headers, JSON object keys) arrives as strings. Python only puts the secret key on str and bytes.

      


      

        
How we got here

        
    
          
  1. 2003Denial of Service via Algorithmic Complexity AttacksScott Crosby and Dan Wallach, USENIX Security. The original paper: make a hash table hit its worst case on purpose, and a small amount of input ties up a server's CPU. They demonstrated it against Perl, the Squid web proxy and the Bro intrusion detector. (abstract page)
    2. 
          
  2. 2011Effective Denial of Service attacks against web application platformsAlexander Klink and Julian Wälde, at the 28th Chaos Communication Congress (talk video). They showed that a single POST request could do it to PHP, Java, Python, Ruby and others. The oCERT-2011-003 advisory warned of "100% of CPU usage which can last up to several hours."
    3. 
          
  3. 2012Python adds hash randomizationA random salt for string hashes, off by default in 2.6.8, 2.7.3, 3.1.5 and 3.2.3 (turn it on with -R), and on by default from Python 3.3. PYTHONHASHSEED controls it.
    4. 
          
  4. 2012Hash-flooding DoS reloaded: attacks and defensesJean-Philippe Aumasson, Daniel J. Bernstein and Martin Boßlet, at the 29th Chaos Communication Congress. Adding a random salt to a weak hash isn't enough: attackers could still find collisions, or work out the salt. Their answer was a hash designed to be keyed: SipHash.
    5. 
          
  5. 2014Python 3.4: SipHash-2-4PEP 456, by Christian Heimes, replaces the salted FNV hash for str and bytes.
    6. 
          
  6. 2022Python 3.11: SipHash-1-3Fewer rounds for speed, keeping the secret key (the discussion).

From hash to bucket

    

      
Whichever recipe ran, the dict gets one 64-bit number. It keeps the lowest bits for the first bucket to try, hash & (size - 1), and if that bucket's taken, it mixes in higher bits with perturb to choose the next one. Try it on The Hash Ring, and see how full the table is allowed to get in Choosing a Load Factor.
