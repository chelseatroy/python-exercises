Session 3 · Follow-up to The Growing List

Where Blocks Live

A list's slots have to sit in one unbroken run of memory. So when the list grows, where does the bigger block come from? Is it ever the same block, just longer? And what happens when there's no room at all?

Part 1

Small blocks: same-size cells

Python makes a lot of small objects, so CPython keeps its own allocator for anything 512 bytes or smaller, called pymalloc. It carves memory into pools, and every pool is cut into cells of one size: a pool of 32-byte cells, a pool of 48-byte cells, a pool of 64-byte cells, and so on in steps of 16 bytes. A small block always lives in one cell.

When a list asks to grow (realloc), pymalloc checks one thing: does the new size still fit in the cell this block already has? If yes, nothing moves. If no, it takes a free cell from a bigger pool, copies the pointers over, and frees the old cell.

Part 2

Bigger blocks: is the memory next door free?

Once a block is bigger than 512 bytes, pymalloc hands the request to the operating system's C library: malloc and realloc. There are no fixed cells here. Memory is one long row of addresses, with other objects scattered along it.

realloc tries the cheap thing first: if the addresses right after the block are free, it just claims them. The block grows in place and nothing is copied. If something is in the way, it has to find a free run long enough for the whole new block somewhere else, and copy. If there's no run long enough anywhere, it gives up and returns NULL, which Python turns into a MemoryError.

This strip is tiny on purpose, so it fills up fast. A real 64-bit program has about 128 terabytes of addresses to choose from, so running out of addresses like this almost never happens. You can still hit it on a 32-bit system, or when a limit is set with ulimit -v. What runs out first in real life is RAM, which is Part 3.

Really big blocks (128 KiB and up, with Linux's default allocator) don't share a row with other objects at all. Each gets its own whole pages straight from the operating system, and growing one can remap those pages to new addresses instead of copying a single byte.

Part 3

Consecutive addresses, scattered RAM

Here's the twist: the addresses your program sees aren't locations in RAM. Every program gets its own private, made-up set of addresses, called virtual addresses. The operating system cuts them into 4 KiB pages and keeps a table, the page table, that says which piece of physical RAM (a frame) each page really uses. The CPU looks every memory access up in that table, in hardware, so it's fast.

So "the slots are contiguous" means the addresses are consecutive. The RAM behind them can be anywhere.

Think of a playlist.

Your playlist numbers its songs 1, 2, 3, 4… in order, and the app can jump straight to song 7. That's a[6]. But the song files are stored on servers all over the place, and the app keeps a lookup from "position in my playlist" to "where the file actually lives". Adding a song never means moving the other files around; only the numbering has to stay in order.

Where it breaks down: the lookup isn't per song but per page, a chunk of 512 pointers. So it's a playlist whose albums can be stored anywhere, but each album's tracks are stored together.

Linux usually says yes to malloc even when RAM is short, and hands out the real frames later, the first time a page is written. That's called overcommit. If no frame is left by then, the out-of-memory killer ends a process, and there's no exception to catch. Container memory limits on Linux behave the same way: the container's process gets killed. Real systems also have swap, disk space used as overflow RAM, which puts all of this off at the cost of making everything very slow.

Try it in Python

A request so big it can't possibly fit fails right away, before any memory is touched:

>>> [None] * 2**62
MemoryError

On Linux, you can cap how many addresses your program may use and watch an ordinary-sized request fail. After the MemoryError, the program is still running, and the list is untouched:

import resource
resource.setrlimit(resource.RLIMIT_AS, (2**30, 2**30))  # 1 GiB of addresses

a = [1, 2, 3]
try:
    a.extend([None] * 200_000_000)  # 1.6 GB of slots
except MemoryError:
    print("MemoryError, and a is still", a)
