Session 6 · How Python runs your code

The Stack Machine

Before Python runs your code, it compiles it into bytecode: a list of tiny instructions like LOAD_FAST and BINARY_ADD. Then a loop in the interpreter runs those instructions one at a time. Almost every one of them does the same kind of thing: it pushes values onto a stack, or pops them off. Here's what that looks like.

This page goes with the disassembly notebook. Every listing below is real output from dis.dis() in Python 3.10.8, the version the notebook runs on. Newer Pythons print something different; the last section shows you what, and why.

From source code to a running loop

1 · You write
def add_two_numbers(a, b):
    return a + b
2 · The compiler makes

A code object: the instructions as bytes, plus a table of constants and a list of variable names.

3 · dis shows you
LOAD_FAST    0 (a)
LOAD_FAST    1 (b)
BINARY_ADD
RETURN_VALUE
4 · The interpreter

Runs one instruction, moves to the next, and repeats until something says RETURN_VALUE.

That interpreter is, at its heart, one enormous loop with a switch statement inside it: one case for every kind of instruction. In Python-flavored pseudocode:

# the shape of CPython's main loop (the real one is C, in Python/ceval.c)
while True:
    instruction = code[next_offset]
    next_offset += 2                      # each 3.10 instruction is 2 bytes
    match instruction.name:
        case "LOAD_FAST":   stack.push(slots[instruction.arg])
        case "BINARY_ADD":  right = stack.pop(); left = stack.pop(); stack.push(left + right)
        case "RETURN_VALUE": return stack.pop()
        ...                               # about 125 more cases

Two different things in there are called "the stack," and they're worth keeping apart:

  • The call stack is a stack of frames, one for every function call that hasn't returned yet. Calling a function pushes a frame; returning pops it. This is what a traceback prints.
  • The value stack lives inside each frame. It's the scratch space the instructions work on: LOAD_FAST pushes onto it, BINARY_ADD pops two values off it and pushes one back.

Each frame also has slots for its local variables, and remembers which instruction it's on.

      Why is it called LOAD_FAST? Is there a LOAD_SLOW?

      There's no instruction called LOAD_SLOW. But there is a slow way to load a variable, and it's what FAST is being compared to: looking the name up in a dictionary.

      The notebook's "Storing and loading names" section disassembles the same loop twice. The first cell puts it inside a function. The second passes it to dis as a string, which dis compiles the way it would compile the top level of a module (or a notebook cell). Same Python, same structure, but every highlighted instruction is different.

      Notebook cell: inside a function
      Outputlocals are numbered slots
      Notebook cell: at module level
      Outputnames live in a dictionary

      The line numbers in the second listing start at 2 because the string starts with a line break, right after the opening """.

      Inside a function, the compiler can see every variable the function will ever have. It reads the whole def before running any of it, so it knows result and item are local, numbers them (slot 3, slot 4), and bakes those numbers into the bytecode. At run time, LOAD_FAST 3 means "give me slot 3": one array index.

      At module level, it can't. Any code anywhere can add a global (import, globals()["x"] = 1, another module doing your_module.x = 1), so names have to be looked up by name, every time. LOAD_NAME checks the local dictionary, then the global dictionary, then the builtins.

      Does the difference matter? The notebook's next two cells time the same sum both ways:

      Reading the C

      You don't have to take my word for it. Here are both instructions, quoted exactly from CPython 3.10.8's Python/ceval.c. Click a line number to see it on GitHub.

      LOAD_FAST: 12 linesGETLOCAL(i) is fastlocals[i]
      LOAD_NAME: 63 linesup to three dictionary lookups

      The other loads that come up, from fastest to slowest-ish:

      • LOAD_CONST: an index into the code object's constants. As cheap as LOAD_FAST.
      • LOAD_DEREF: a variable from an enclosing function, for closures. One extra hop through a "cell" object.
      • LOAD_GLOBAL: used inside functions for names that aren't local, like range or another function you defined. Two dictionary lookups: globals, then builtins.
      • LOAD_NAME: module-level code. Up to three dictionary lookups.
      • LOAD_ATTR: obj.thing. Can involve the instance's dictionary, its class, every parent class, and descriptors like @property.

      The interpreter rewrites the bytecode while it runs
      
    
      
      
      This is the biggest change, and it's the real answer to "how does Python get faster without changing my code." Since 3.11, after an instruction has run a few times, the interpreter swaps it for a specialized version based on what it actually saw. BINARY_OP has to handle + for ints, floats, strings, lists, and your own classes. But if it has only ever seen two ints, it becomes BINARY_OP_ADD_INT, which skips the "what type is this?" checks. If a different type ever shows up, it switches back. You can watch it happen with dis.dis(f, adaptive=True).
