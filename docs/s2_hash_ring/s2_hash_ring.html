Session 2 · How a dict works under the hood

The Hash Ring

Under every Python dict is a plain, fixed-size array. Each slot is called a bucket. So how does d["greeting"] find the right bucket right away, without searching?

A good hash function is…

1Deterministic

Same input, same output. Every time.

hash(key)
random.choice(key)

Try it: run python3 -c "print(hash('greeting'))" twice. Different numbers! Python salts string hashes freshly for each run. Within one run the hash never changes, and that's all a dict needs.

2Fast

Every d[key] starts by hashing key. Hashing is part of every lookup, so it has to be cheap.

—

Password hashes like bcrypt are slow on purpose, around 0.1 s each, so attackers can't guess quickly. A dict that used one would need about 2 minutes to look up 1,000 keys.

3Uniform

Hashes spread keys evenly over the buckets, so no bucket gets crowded. (The word for this really is uniformity.)

Round and round the ring

The array is bent into a ring around the hash function. The hash gives a big number. The number counts its way around the ring, lap after lap. Wherever it stops (the remainder, hash % size) is the bucket.

    Two ways to handle a collision

    Same five keys, same 8 buckets. Say 'thanking' and 'apologizing' both hash to bucket 0, which 'greeting' already holds.

    Separate chaining

    Colliding keys form a linked list hanging off the bucket. Finding one means walking the list. If every key lands in one bucket, a lookup is a linear search: O(n).

    Open addressing

    Every key lives in the array itself. If its bucket is taken, it probes: it tries another bucket by a fixed rule until one is empty. Finding it later means following the same trail.

    Why doesn't Python just do +1? (Clustering)

    Try "the next one (+1)" vs "Python's jump" on the ring first.

    With +1, colliding keys pile up in a run of full neighboring buckets, called a cluster. Any key that lands anywhere in a cluster has to walk to the end of it, and the cluster grows. A bad enough cluster is a linear search, just like a long chain: O(n). Python's jump mixes in more of the hash every step, so the trail scatters around the ring:

    perturb = hash
i = hash % size
while bucket i is taken:
    perturb >>= 5
    i = (5*i + 1 + perturb) % size

    Once perturb shifts down to 0, 5*i + 1 still reaches every bucket, as long as the size is a power of 2. That's one reason a CPython dict's array size is always a power of 2 (8, 16, 32, …).

    When do the tombstones finally go away?

    Guess first. Then try "Watch it grow" or "Shrink?" on the ring.

    When the array is resized. Every key gets re-hashed into a brand-new array, so every trail is rebuilt from scratch, and the tombstones are no longer needed. Until then they take up space: we spend space to keep lookups correct.

    Same hash, new size, so a different remainder. That's why keys land in different buckets after a resize.

    Separate chaining doesn't need tombstones: unlink the node and stitch the list back together. (Linked lists are made for that.)

    "Tombstone" is a general programming word: mark it deleted instead of deleting it, so everything else keeps working. Databases like Cassandra (built at Facebook) do it, and your homework's transactions will need one too.

    Load factor: how full before it grows?

    Load factor = keys ÷ buckets. A fuller array wastes less space but gets more collisions. Pick the rules, then drag through 1,000 inserts.

    And shrinking?

    Deleting never shrinks a dict.Delete 1,000 keys one by one: same size in memory.
    Deleted slots stay used up.They're tombstones until the next resize.
    Only an insert can resize.When it finds 2/3 of the buckets used up.
    New size: power of 2 ≥ 3 × live keys.Under ~1/6 full: it shrinks. Otherwise it stays the same or grows.
    d.clear() shrinks right away.Back to an empty dict.

    So a dict with lots of room left can go from 1,000 keys down to 5 and stay big for another 1,361 inserts. Then it grows. Try it yourself:

    import sys
d = {i: i for i in range(21)}   # 21 keys: 2/3 of 32 buckets, as full as allowed
print(sys.getsizeof(d))
for i in range(5, 21):
    del d[i]                     # down to 5 keys...
print(sys.getsizeof(d))          # ...same size!
d["one more"] = 1                # an insert finds nothing usable left → resize
print(sys.getsizeof(d))          # smaller: 3 × 5 = 15 → 16 buckets

    Measured in CPython 3.10, 3.11, 3.13 and 3.14.
