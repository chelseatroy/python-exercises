Choosing a Load Factor

A Python dict grows when its buckets are 2/3 full. Why 2/3, and not 1/2 or 9/10? Whatever load factor you pick, you're trading speed for memory or memory for speed. Slide it and watch both sides of the trade.

Fuller is slower. Emptier is bigger.

Load factor = keys ÷ buckets. These curves assume a good hash function and probing that scatters, like Python's jump. Real tables come close to them.

Since Python 3.6, the empty buckets cost less than this chart suggests. Each key's entry (its hash, key, and value: 16 to 24 bytes) sits in a packed list of entries. The bucket array only holds small index numbers pointing into that list: 1 byte each for up to 128 buckets, growing to 8 bytes in huge dicts. So an empty bucket costs a few bytes, not a whole entry.

What load factor does to the chance of a collision

When a new key arrives, its hash picks a bucket at random (that's the "uniform" in a good hash function). If the table is a fraction α full, the chance that bucket is already taken is simply α. At 2/3 full, a new key collides 2 times out of 3.

If it collides, it probes another bucket, which is also taken with chance about α. So the chance of needing 3 or more checks is about α × α, 4 or more is α³, and so on. The collision chance grows in a straight line, but the cost multiplies, which is why the curve above shoots up near 1.

Lowering the load factor doesn't prevent collisions

The chance that this key collides is α. But a table fills one key at a time, and the chance that some key has collided by now climbs much faster. It's the birthday problem: with 23 people, two probably share a birthday, even though there are 365 days.

So no sensible load factor avoids collisions; even a table that's 5% full has almost surely had some. What the load factor controls is how long the trail is when a collision happens. That's why the time chart above measures checks, not collisions.

Both axes are log scales: each step up multiplies, instead of adding. Work counts bucket checks, plus one move for every key copied during a resize.

Expected O(1): lookups

A lookup never resizes, so there's no expensive step to spread out. Its cost depends on where keys happened to land. Averaged over that luck, it's at most 3 checks at any size. That's expected (or average-case) O(1). It's only true if the hash spreads keys evenly: with every key on the same hash, it's O(n).

Amortized O(1): inserts

Most inserts are cheap, and every so often one is very expensive. Each resize copies every key, but it also doubles the room, so the next resize waits twice as long. Spread over all the inserts, the copying adds up to about 2 extra moves per key at most. That's amortized O(1): an average over a whole run of operations. It's the same trick as list.append in Session 3.

Why does Python give string hashes a fresh random salt every run? If attackers could predict the hashes, they could send a web server thousands of keys that all collide, turning every dict insert into O(n) work and tying up the server. That's called hash flooding.

Try it in Python

Lookup time as the collection grows 1,000×:

import timeit

for n in [1_000, 10_000, 100_000, 1_000_000]:
    d = dict.fromkeys(range(n))
    lst = list(range(n))
    t_dict = timeit.timeit(lambda: -1 in d, number=1000) / 1000
    t_list = timeit.timeit(lambda: -1 in lst, number=100) / 100
    print(f"{n:>9,} keys   dict {t_dict * 1e9:5.0f} ns   list {t_list * 1e9:12,.0f} ns")
    1,000 keys   dict    43 ns   list        4,950 ns
   10,000 keys   dict    40 ns   list       50,062 ns
  100,000 keys   dict    42 ns   list      526,338 ns
1,000,000 keys   dict    46 ns   list    5,339,003 ns

And with a hash that sends every key to the same bucket. Double the keys, and the time goes up 4×: each insert walks past every key already there.

import time

class SameHash:
    def __hash__(self):
        return 0          # every key lands in the same bucket

for n in [2_000, 4_000, 8_000, 16_000]:
    start = time.perf_counter()
    d = {SameHash(): None for _ in range(n)}
    print(f"{n:>5,} keys   {time.perf_counter() - start:.2f} s")
2,000 keys   0.02 s
4,000 keys   0.09 s
8,000 keys   0.34 s
16,000 keys   1.38 s

One run on CPython 3.10. Your times will differ, but the pattern won't.

So why about 0.7?

Where the curves bend

  • Above about 0.7, time gets expensive fast. A new key needs 3 checks on average at 2/3, 5 at 0.8, and 10 at 0.9.
  • Below about 0.5, space gets expensive fast. Going from 2/3 to 1/2 cuts a miss from 3 checks to 2, but takes a third more memory. Going from 1/2 to 1/4 doubles the memory again, and saves less than one check.
  • Remember the resize. Right after a dict doubles, it's only 1/3 full. The 2/3 is the worst it ever gets, so most of the time a dict is somewhere between 1/3 and 2/3 full.
  • It's cheap to compute. CPython writes the limit as (n << 1) / 3: integer arithmetic, no floats.

There's no theorem that says 2/3. CPython's developers timed real programs at different settings and kept the one that did well. Their notes are in Objects/dictnotes.txt.

Other tables, other answers

TableGrows atWhy
Python dict2/3The balance above.
Python set3/5Sets mostly answer x in s, and many of those answers are "no". Misses are the expensive case, so sets stay emptier.
Java HashMap3/4Uses chaining, so a busy bucket just gets a longer list, with no probing at all. You can even set its load factor above 1.
Rust HashMap, Abseil, Go 1.24+7/8"Swiss tables" check a whole group of 8 or 16 buckets in one CPU instruction, so a longer trail costs much less.

The right number depends on how much each extra check costs. Make checks cheaper and you can pack the table fuller.
